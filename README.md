# AgentScan

Мини-сканер процесса Minecraft (Java Edition, HotSpot JVM под Windows x64). Он ищет
**следы JVMTI-агентов, Java-агентов (`java.lang.instrument`) и вмешательства в
окружение виртуальной машины**. Находит и агента, который работает сейчас, и агента,
который уже отключился.

Главная идея: подключение агента необратимо меняет состояние виртуальной машины. Код
агента можно выгрузить, трансформер снять, окружение JVMTI отключить. Но ВМ всё равно
помнит, что агент был:

- запись в собственном списке агентов;
- окружение JVMTI с магическим числом «отключено»;
- флаг, выставленный механизмом attach;
- запись о подмене класса в кольцевом журнале;
- счётчик подмен в зеркале класса.

AgentScan читает эти записи из памяти процесса, не останавливая игру и не подключаясь
к ней отладчиком.

## Быстрый старт

### Окно

Запустите `AgentScan.exe` двойным щелчком, лучше **от имени администратора**.

1. В списке сразу показаны процессы `javaw.exe` и `java.exe` в виде
   `PID Заголовок окна - память в ГБ`, например `4992 Minecraft* 1.21.10 - 1,17 ГБ`.
   Окна Minecraft стоят сверху и выбраны заранее. Если игру запустили позже, нажмите
   «Обновить».
2. «Проверить»: полоса показывает ход проверки, под ней текущий шаг (у сплошного скана
   памяти ещё и проценты).
3. В конце видны вывод (красный, жёлтый или зелёный) и счётчики находок. Две кнопки:
   - **«Результат»** открывает папку `reports` и выделяет HTML-отчёт;
   - **«В браузере»** открывает отчёт в браузере по умолчанию. Браузер берётся из
     обработчика ссылок `http`, а не из связки файлов `.html`: она часто указывает на
     редактор.

Если окно закрыть во время проверки, сканер спросит подтверждение и закроется после
текущего шага.

Без прав администратора внизу окна будет предупреждение: тогда доступны только
процессы текущего пользователя.

### Консоль

Любой ключ включает консольный режим (вывод и коды возврата прежние):

```bat
AgentScan.exe --console
AgentScan.exe --pid 1234
AgentScan.exe --list
```

С `--console` процесс Minecraft ищется автоматически. Если подходящих процессов
несколько, укажите `--pid`. Exe собран как оконная программа, поэтому в `cmd`
приглашение вернётся раньше, чем закончится вывод. Чтобы дождаться конца и получить код
возврата, запускайте через `start /wait AgentScan.exe --pid 1234`. В PowerShell при
перенаправлении вывода (`| ...`, `> файл`) ожидание происходит само.

На проверяемой машине .NET не нужен, если брать полный `AgentScan.exe` (self-contained,
один файл). Облегчённому `AgentScan-lite.exe` (~1 МБ) нужен .NET 8 Desktop Runtime —
см. [Сборка](#сборка).

| Ключ | Что делает |
|---|---|
| `--pid, -p <N>` | PID процесса игры (по умолчанию ищется автоматически) |
| `--list, -l` | показать Java-процессы и выйти |
| `--console, -c` | консольный режим с автоматическим поиском процесса |
| `--out, -o <dir>` | каталог для отчётов (по умолчанию `reports` рядом с exe) |
| `--dump-dir <dir>` | каталог для дампов найденных остатков |
| `--verbose, -v` | подробный вывод в консоль |
| `--max-dump <МБ>` | предел на один дамп (по умолчанию 256 МБ) |
| `--no-strings` | пропустить сплошной скан памяти: быстро, но часть проверок останется без данных |
| `--no-dump` | не сохранять дампы |
| `--fast` | то же, что `--no-strings --no-dump` |
| `--only <часть,...>` | выполнить только шаги, в имени которых есть подстрока (отладка сканера; отчёт помечается неполным) |
| `--skip <часть,...>` | пропустить такие шаги |

## Что выводится

Формат тот же, что у McScanner:

1. **Консоль** (в окне — вывод и счётчики): находки сгруппированы по значимости (КРИТИЧНО → ВЫСОКАЯ → СРЕДНЯЯ →
   НИЗКАЯ). Внизу итоговые счётчики, время и вывод одной строкой.
2. **`reports/agentscan-<pid>-<время>.html`**: отчёт для разбора глазами. В нём вердикт,
   счётчики, фильтры по значимости и категории, поиск, тёмная и светлая тема. У каждой
   находки есть объяснение механики и сырые данные. Вкладка «Полные данные» содержит
   полные разделы: окружения JVMTI, флаги ВМ, журналы событий, свойства среды.
3. **`agentscan-<pid>-<время>.txt`**: тот же отчёт полным текстом.
4. **`agentscan-<pid>-<время>.json`**: для автоматической обработки.
5. **`reports/agentscan-dumps-<время>/`**: дампы найденных остатков (окружений, записей
   агентов, структур JPLIS), если они есть.

Значимость находок:

| Уровень | Смысл |
|---|---|
| **CRITICAL** | практически однозначная улика |
| **HIGH** | сильный признак, требует объяснения |
| **MEDIUM** | нужна ручная проверка |
| **LOW** | слабая аномалия, бывает и у чистого процесса |
| **INFO** | справка, не улика |

Коды возврата: `10` — есть CRITICAL, `9` — есть HIGH, `8` — есть MEDIUM, `0` — чисто,
`2` — процесс не найден, `3` — фатальная ошибка.

## Что находит

Ниже все проверки по группам. Значимость указана такой, какую выставляет сам сканер.

### 1. Окружения JVMTI

Окружение JVMTI (`JvmtiEnvBase`) — объект, который ВМ заводит каждому агенту на вызове
`GetEnv(JVMTI_VERSION)`. Оно хранит всё, что агент просил у машины. **При отключении
агента объект не удаляется**: HotSpot только меняет магическое число с `0x71EE`
(активно) на `0xDEFC` (отключено через `DisposeEnvironment`).

| Проверка | Что ищется | Значимость |
|---|---|---|
| **Список окружений ВМ** (обход `JvmtiEnvBase::_head_environment` по живому VMStructs) | все окружения, включая отключённые; магическое число и состояние | CRITICAL |
| **Окружения вне списка** | объекты окружения, найденные в памяти, но отвязанные от списка ВМ | CRITICAL |
| **Подписка на `ClassFileLoadHook`** | агент получает байт-код каждого загружаемого класса и может его переписать | CRITICAL |
| **Колбэки событий в никуда** | обработчики событий ведут в память вне загруженных модулей: библиотека агента выгружена, а окружение помнит её адреса | CRITICAL |
| **Возможности агента** (`jvmtiCapabilities`) | 45 именованных возможностей, которые агент запросил: `can_redefine_classes`, `can_retransform_classes`, `can_generate_breakpoint_events`, `can_tag_objects`… Они остаются записанными навсегда | в составе находки |
| **Таблица тегов объектов** | агент помечал объекты кучи; восстанавливаются классы помеченных объектов | CRITICAL |
| **Префиксы нативных методов** (`SetNativeMethodPrefix`) | строки, которые задал сам автор агента | CRITICAL |
| **Собственные данные агента** (`_env_local_storage`) | указатель на структуру агента, дамп и строки из неё | CRITICAL |
| **Статические флаги `JvmtiExport`** | `_can_hotswap_or_post_breakpoint`, `_can_access_local_variables`, `_can_post_on_exceptions`, `_can_walk_any_space`. ВМ взводит их, когда агент запрашивает соответствующие возможности | CRITICAL |
| **Точки останова JVMTI** | ненулевой `InstanceKlass::_breakpoints` или счётчик точек останова у метода. Заполняет только `SetBreakpoint` | CRITICAL |
| **Объекты `JvmtiAgentThread`, `JvmtiBreakpoint`** | поиск по точному адресу vtable из экспортов `jvm.dll` | CRITICAL |
| **Независимый поиск по магическому числу** | окружения ищутся по `0x71EE/0xDEFC/0xDEAD` со структурной проверкой (версия JVMTI, `_next`, 37 слотов колбэков, обратная ссылка таблицы тегов). Затирание указателя на vtable не помогает | CRITICAL |
| **Структуры, держащие окружение** | кто хранит указатель на `jvmtiEnv`: `JPLISAgent` (нативная часть `java.lang.instrument`) или собственные структуры нативного агента | HIGH / CRITICAL |
| **Таблицы `jvmtiInterface_1_` / `JNINativeInterface_`** | слоты таблиц функций в `jvm.dll`, перенаправленные за её пределы (перехват) | CRITICAL |
| **Таблица `JavaVM`** (`JNIInvokeInterface_`) | `AttachCurrentThread`/`GetEnv` перенаправлены за пределы `jvm.dll` | CRITICAL |

Окружение, все обработчики которого ведут внутрь самой `jvm.dll`, считается служебным
(так своё окружение заводит Flight Recorder) и посторонним агентом не объявляется.

### 2. Java-агенты и механизм attach

| Проверка | Что ищется | Значимость |
|---|---|---|
| **Список агентов HotSpot** (`JvmtiAgentList` в JDK 21, `AgentLibrary` в JDK 8–17) | Запись об агенте не удаляется даже после `Agent_OnUnload`. Из неё читаются имя, опции (для Java-агента это путь к его jar), путь к библиотеке, дескриптор библиотеки (выгружена ли она) и указатель JPLIS. На JDK 21+ читается и флаг «подключён к работающей ВМ» | CRITICAL (attach или неизвестный агент), HIGH (известный агент при запуске) |
| **Объекты механизма attach** (`AttachOperation`, `Win32AttachOperation`, `JVMTIAgentLoadDCmd`) | объект с **заполненным** именем команды (`load`, `jcmd`, `setflag`…): к работающей ВМ приходили команды извне | CRITICAL |
| **Флаги ВМ: источник `ATTACH_ON_DEMAND`** | флаг, изменённый через attach на работающей ВМ. Разряд источника живёт в статических данных `jvm.dll`, стереть его нечем | CRITICAL |
| **Флаги ВМ: источник `MANAGEMENT`** | настройку сменили изнутри процесса через `HotSpotDiagnosticMXBean`. Игра так не делает | HIGH |
| **Аргументы агентов в копии ВМ** | `-javaagent`, `-agentlib`, `-agentpath`, `-Xbootclasspath` в собственной копии аргументов ВМ (`Arguments::_jvm_args_array`) | CRITICAL |
| **Сверка трёх копий командной строки** | копия ВМ, блок параметров процесса (PEB), счётчики hsperfdata. Аргумент есть у ВМ, но нет в PEB: пришёл из `JAVA_TOOL_OPTIONS` или PEB подчистили. Флаг помечен командной строкой, но его нет в копии аргументов: значение записано в обход разбора аргументов | HIGH / CRITICAL |
| **Флаги, связанные с подключением** | `EnableDynamicAgentLoading`, `DisableAttachMechanism`, `StartAttachListener`, `AllowRedefinitionToAddDeleteMethods`, `UnlockDiagnosticVMOptions` и другие, заданные явно | MEDIUM / HIGH |
| **Переменные окружения** | `JAVA_TOOL_OPTIONS`, `_JAVA_OPTIONS`, `JDK_JAVA_OPTIONS`. С ключом агента — CRITICAL; непустая без агента — MEDIUM (TLauncher ставит пустую `_JAVA_OPTIONS=`, это INFO) | CRITICAL / MEDIUM |
| **Модули агентов** | загружены `instrument.dll`, `jdwp.dll` (CRITICAL), `attach.dll` (HIGH); любой модуль с экспортами `Agent_OnLoad` / `Agent_OnAttach` / `Agent_OnUnload` (CRITICAL) | CRITICAL / HIGH |
| **Потоки агентов** | `JVMTI Agent Thread` (CRITICAL), `JDWP…` и `Java Debug…` (HIGH). Поток `Attach Listener` на Windows создаётся всегда и уликой не считается | CRITICAL / HIGH |
| **Объект `InstrumentationImpl`** | живой или в мёртвой зоне кучи. **В чистом клиенте на Fabric его нет вообще.** Читаются адрес нативного агента, выторгованные возможности и оба списка трансформеров | CRITICAL |
| **Объекты `ClassFileTransformer`** | все объекты классов, реализующих трансформер, даже снятые с `removeTransformer`, с пометкой, есть ли класс в архивах игры | CRITICAL |
| **Классы механизма агентов** | загружены `sun/instrument/*`, `java/lang/instrument/*` (ВМ грузит их только при подключении агента и не выгружает) | HIGH |
| **Байт-код агентских классов в памяти** | `sun/instrument/InstrumentationImpl`, `java/lang/instrument/*`, `sun/tools/attach/*`, `com/sun/tools/attach/VirtualMachine` (CRITICAL), `jdk/internal/agent/` (MEDIUM) | CRITICAL / MEDIUM |
| **Агент в счётчиках hsperfdata** | ключ агента в `java.rt.vmArgs` / `sun.rt.javaCommand`: что ВМ записала о себе при запуске, независимо от PEB | CRITICAL |
| **Область hsperfdata не найдена** | её отключили `-XX:-UsePerfData` / `-XX:+PerfDisableSharedMem`, чтобы нечем было сверить запуск | HIGH (MEDIUM, если ключ виден) |

### 3. Чёрный ящик ВМ и переопределение классов

HotSpot пишет кольцевые журналы событий для отчёта о падении (`Events::log`). Они
переживают отключение агента и выгрузку его классов.

| Проверка | Что ищется | Значимость |
|---|---|---|
| **Журнал `Classes redefined`** | любая запись: имена подменённых классов и время подмены. Пишет только `RedefineClasses` / `RetransformClasses` | CRITICAL |
| **Выгрузка нативных библиотек** (`Unloaded dll`) | клиент Minecraft свои библиотеки не выгружает | CRITICAL |
| **Библиотеки из журнала, которых нет в процессе** | ВМ помнит загрузку, а модуля уже нет | CRITICAL |
| **Поздно загруженные библиотеки** | загружены значительно позже остальных | HIGH |
| **Классы из журналов загрузки и выгрузки, которых нет в архивах игры** | | HIGH / CRITICAL |
| **Пустые журналы при работе больше минуты** | содержимое затёрли: сама ВМ счётчик записей не обнуляет | CRITICAL |
| **`-XX:-LogEvents` / урезанный `LogEventsBufferEntries`** | бортовой самописец выключен намеренно | HIGH |
| **Операции агента в кольце `VM Operations`** | `RedefineClasses`, `ChangeBreakpoints`, `GetOrSetLocal`, `HeapWalkOperation`, `GetAllStackTraces`, `ForceEarlyReturn`… Игра их не вызывает никогда | HIGH |
| **Флаги переопределения у методов** | `IS_OLD`, `IS_OBSOLETE`, `IS_DELETED`, `IS_PREFIXED_NATIVE` у объектов `Method`. Ставят только `RedefineClasses`, `RetransformClasses` и `SetNativeMethodPrefix` | CRITICAL |
| **Осиротевшие метаданные** | объекты `Klass`/`Method`/`ConstantPool`, недостижимые из графа загрузчиков, с осмысленными (не рантаймовыми) именами: остатки старых версий подменённых классов | MEDIUM |
| **Счётчик подмен в зеркале класса** (`Class.classRedefinedCount`) | точный учёт подмен по каждому классу за всю жизнь процесса, включая классы, которые журнал на 20 записей уже вытеснил | CRITICAL |
| **Несколько копий байт-кода одного класса** | след трансформации (исходные и изменённые байты) | INFO |
| **Сведение четырёх источников** (журнал, флаги методов, недействительный скомпилированный код, счётчики в зеркалах) | рассогласования: флаги есть, а журнал пуст (журнал затёрли); журнал есть, а флагов нет; мёртвый код в кодовом кеше без записей о выбросе. Сюда же сплошные полосы недействительного кода по номерам компиляции (класс выбит целиком) и плотные всплески деоптимизации | CRITICAL / HIGH / MEDIUM |

### 4. Окружение Java

| Проверка | Что ищется | Значимость |
|---|---|---|
| **`jdk.attach.allowAttachSelf=true`** | процессу разрешено подключиться механизмом attach к самому себе: так код, уже работающий внутри игры, подсаживает в неё агента без внешнего загрузчика | CRITICAL |
| **`System.props` против снимка `VM.savedProps`** | свойства, добавленные уже работающим кодом; переписанные опорные свойства (`java.class.path`, `java.library.path`, `sun.boot.library.path`, `java.home`, `java.system.class.loader`…); свойства, удалённые `System.clearProperty` | HIGH / MEDIUM |
| **Открытые пакеты `java.base`** | `--add-opens` или `Modules.addOpens` на ходу. Карта открытий не очищается никогда; у чистого клиента открытий `java.base` ноль | HIGH |
| **Нативные библиотеки глазами Java** (`NativeLibraries`) | библиотека числится загруженной у Java, но её модуля в процессе нет (выгружена); библиотеку загрузил класс, которого нет ни в одном архиве игры | HIGH / CRITICAL |
| **Классы в привилегированных загрузчиках** | класс не из JDK в начальном или платформенном загрузчике. Так работают `-Xbootclasspath/a`, `Instrumentation.appendToBootstrapClassLoaderSearch` и JNI `DefineClass` с пустым загрузчиком | CRITICAL |
| **Загрузчик, сам являющийся скрытым классом** | код загружен загрузчиком, чьё имя нельзя найти | CRITICAL |
| **Лишний нулевой загрузчик** | больше одного `ClassLoaderData` без объекта-загрузчика и без признака скрытого класса | HIGH |

### 5. Сигнатуры в памяти

Сплошной скан всей памяти процесса за один проход. Набор строк — только механизмы
JVMTI, `java.lang.instrument` и attach. Каждая строка ищется лишь там, где её не может
быть у чистой ВМ (например, только в приватной исполняемой памяти: в `jvm.dll` и в
`lib/modules` эти строки есть всегда).

| Строка | Где ищется | Значимость |
|---|---|---|
| `Agent_OnAttach`, `Agent_OnUnload` | приватная исполняемая | HIGH |
| имена функций JVMTI: `RetransformClasses`, `RedefineClasses`, `GetLoadedClasses`, `SetEventNotificationMode`, `AddCapabilities`, `IterateOverInstancesOfClass`, `GetObjectsWithTags`, `FollowReferences`, `DisposeEnvironment` | приватная исполняемая | HIGH |
| `SetJNIFunctionTable`, `GetJNIFunctionTable` | приватная исполняемая | CRITICAL |
| `JNI_GetCreatedJavaVMs`, `AttachCurrentThread` | приватная исполняемая | HIGH |
| `\\.\pipe\javatool` (канал Dynamic Attach) | приватная | CRITICAL |
| `JPLISAgent`, `loadAgentLibrary`, `loadClassAndCallPremain`, `loadClassAndCallAgentmain` | приватная | HIGH |
| `appendToSystemClassLoaderSearch`, `appendToBootstrapClassLoaderSearch` | приватная | CRITICAL |
| `net/bytebuddy/agent`, `net/bytebuddy/` | приватная | HIGH |
| `javassist/`, `redefineModule` | приватная | MEDIUM |
| `sun/instrument/InstrumentationImpl`, `TransformerManager`, `addTransformer`, `retransformClasses`, `defineAnonymousClass` | приватная | LOW: одиночные вхождения бывают и в чистой ВМ, доказательна только структурная проверка |

Набор дополняется файлом `signatures.json` рядом с exe (массив объектов
`{name, category, text, severity, scope, utf16, wholeWord, note}`).

## Как это устроено

1. **Основа.** Карта памяти, модули, потоки, таблицы JNI/JVMTI в данных `jvm.dll`.
2. **Живой VMStructs.** Из экспортов `jvm.dll` читается `gHotSpotVMStructs`: таблица
   настоящих смещений полей этой сборки HotSpot. По ней обходятся граф загрузчиков
   классов, список окружений JVMTI, таблица флагов ВМ и копия аргументов. Смещения не
   зашиты в код, поэтому сканер переносим между выпусками JDK.
3. **Сплошной скан памяти.** Один проход по всей читаемой памяти. За него находятся
   сигнатуры, class-файлы Java, объекты метапространства по точным адресам vtable,
   объекты журналов событий ВМ и ссылки на таблицы JNI/JVMTI.
4. **Куча Java.** Объекты читаются по именам полей платформы: `InstrumentationImpl`,
   трансформеры, свойства, модули, нативные библиотеки, зеркала классов. Читается и
   мёртвая зона кучи, то есть остатки собранных объектов.
5. **Служебные шаги** (список модулей, имена потоков, блоки кодового кеша) собирают
   только то, что нужно проверкам выше.

Сканер **только читает** память процесса: агентов не подключает, attach не выполняет,
в процесс не пишет и потоки игры не останавливает.

## Ограничения

- **Только Windows x64 и HotSpot** (Oracle/OpenJDK/Temurin и т. п.). OpenJ9 не
  поддерживается.
- **Флаг «подключён к работающей ВМ» в записи агента** читается только на JDK 21+. У
  записи `AgentLibrary` в JDK 8–17 такого поля нет; там способ подключения
  определяется по другим следам: аргументам, объектам attach, флагам ВМ.
- **Нулевой фон ничего не доказывает.** Аккуратный автор обойдёт любой признак
  поодиночке. Сила — в наборе независимых записей одного факта: подделать согласованно
  все сразу (список агентов, окружение, флаги, журнал, счётчики в зеркалах) значительно
  сложнее.
- **Нативный чит без JVMTI и без attach** (прямое чтение и запись памяти) почти не
  оставляет следов, которые ищет AgentScan.
- **Время работы** растёт с размером кучи: сплошной скан и обход метапространства
  читают всю память процесса.
- Сканер проверяет процесс в момент запуска. Журналы событий ВМ кольцевые: самые старые
  записи вытесняются новыми.

## Положительный тест

В `tests/positive/` лежит мишень и тестовый Java-агент: трансформер плюс
`retransformClasses`. `run-test.cmd` поднимает три JVM: без агента, с `-javaagent` и с
агентом, подключённым через `VirtualMachine.loadAgent`. Затем прогоняет AgentScan по
каждой. Нужен JDK 21.

```bat
tests\positive\run-test.cmd
```

Результат на JDK 21.0 (Windows 10):

| Процесс | CRITICAL | HIGH | MEDIUM | Код | Ключевые находки |
|---|---|---|---|---|---|
| без агента | 0 | 0 | 0 | 0 | — |
| `-javaagent` | 25 | 8 | 2 | 10 | запись агента «instrument» с путём к jar и флагом «при запуске», два окружения JVMTI, `ClassFileLoadHook`, `InstrumentationImpl` и трансформер в куче, ключ агента в копии аргументов ВМ и в hsperfdata |
| attach | 27 | 8 | 2 | 10 | запись агента с флагом «к работающей ВМ», `Win32AttachOperation` с командой `load`, запись в журнале `Classes redefined`, операция `RedefineClasses` в кольце VM Operations, счётчик подмен в зеркале класса `Target` |

То же на настоящей игре: Minecraft 1.21.10 (TLauncher, Fabric Loader 0.19.3, JDK 21),
рабочее множество 1,4 ГБ.

| Процесс | CRITICAL | HIGH | MEDIUM | LOW | Время | Код |
|---|---|---|---|---|---|---|
| чистая игра | 0 | 0 | 0 | 3 | 67 с | 0 |
| та же игра после attach тестового агента | 26 | 7 | 2 | 6 | 77 с | 10 |

Три LOW у чистой игры штатные. Это одиночные строки `InstrumentationImpl` (описание
модуля `java.instrument`, которое ВМ разбирает при старте) и «28 аргументов ВМ нет в
командной строке»: TLauncher передаёт их файлом `@args`.

## Сборка

Нужен .NET SDK 8.0 (только на машине сборки).

```bat
build.cmd
```

Собираются два варианта одного и того же сканера:

| Файл | Размер | Что нужно на проверяемой машине |
|---|---|---|
| `dist\AgentScan.exe` | ~70 МБ | ничего: рантайм .NET 8 и WinForms вшиты внутрь (self-contained) |
| `dist\AgentScan-lite.exe` | ~1 МБ | [.NET 8 Desktop Runtime x64](https://dotnet.microsoft.com/download/dotnet/8.0) |

Если у `AgentScan-lite.exe` нет .NET, загрузчик .NET показывает окно «You must install
or update .NET to run this application». Кнопка «Download it now» ведёт на сайт
Microsoft (`aka.ms/dotnet-core-applaunch`). Ставить нужно именно **.NET Desktop Runtime
8 (x64)**: в нём уже есть базовый .NET Runtime. Если поставить только базовый рантайм,
при следующем запуске окно попросит ещё и Desktop Runtime.

Вручную:

```bat
dotnet publish src -c Release -o out-full
dotnet publish src -c Release -o out-lite -p:SelfContained=false -p:EnableCompressionInSingleFile=false -p:PublishReadyToRun=false
```

У облегчённого варианта ReadyToRun отключён намеренно. В связке «один файл + без
рантайма» exe с ReadyToRun падал при старте внутри `coreclr.dll` (`0xC0000602`,
проверено на .NET 8.0.27). На работу сканера это не влияет, только на время запуска.

Структура:

```
AgentScan/
  README.md            это описание
  build.cmd            сборка: полный dist\AgentScan.exe и облегчённый dist\AgentScan-lite.exe
  src/
    Program.cs         разбор ключей, консольный режим, запуск скана и запись отчётов
    Gui/MainForm.cs    окно: список процессов, полоса хода, кнопки отчёта
    Analysis/          проверки и конвейер (Scanner.cs)
    Core/              чтение процесса, карта памяти, VMStructs, куча Java, индекс jar
    Native/            вызовы ntdll/kernel32
    Report/            консоль, HTML, TXT, JSON
  tests/positive/      мишень и тестовый агент
```
